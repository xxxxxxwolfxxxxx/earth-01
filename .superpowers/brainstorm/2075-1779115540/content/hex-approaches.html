Hex-Grid für Earth 0.1 — Welcher Ansatz?

Civilization-Style Hexagonal Kacheln für die 2D-Weltkarte

A

Canvas + Eigenes Hex-Rendering

Wir malen die Hexagone selbst auf den bestehenden HTML Canvas. Keine neue Dependency. Hex-Math (offset coordinates, pixel ↔ hex conversion) kommt aus dem Red Blob Games Guide — dem Standardwerk für Hex-Grids.

Pro

  • Keine neue Library
  • Volle Kontrolle über Look & Feel
  • Leichtgewichtig (~200 Zeilen Hex-Math)
  • Passt perfekt zum bestehenden Canvas-Code

Contra

  • Hex-Math muss korrekt implementiert werden
  • Kein eingebautes Scrolling/Zoom
B

PixiJS (WebGL 2D Engine)

Leistungsstarke 2D-Game-Engine. Rendert Hex-Tiles als Sprites/Polygone mit GPU-Beschleunigung. Großes Ökosystem, viele Hex-Grid-Beispiele.

Pro

  • GPU-beschleunigt, sehr performant
  • Eingebauter Sprite-Support für Tile-Texturen
  • Zoom, Pan, Interaktion out-of-the-box
  • Großes Ökosystem (pixi-viewport, etc.)

Contra

  • ~500KB Bundle-Size
  • Neues Rendering-Paradigma (nicht mehr ctx.fillRect)
  • Komplexere Integration mit React
C

SVG + honeycomb-grid Library

honeycomb-grid ist eine spezialisierte Open-Source Hex-Grid-Library (TypeScript). Berechnet Hex-Koordinaten, Nachbarn, Pathfinding. Rendering via SVG-Polygone.

Pro

  • Hex-Math komplett abstrahiert
  • TypeScript-native, gut getestet
  • SVG = CSS-Styling, Hover-Effekte, Tooltips nativ
  • Kleine Library (~15KB)

Contra

  • SVG wird bei 900 Hexagonen etwas langsam
  • Weniger visueller Charme als Canvas/WebGL
  • Neue Dependency

💡 Meine Empfehlung: Option A

Für 30×30 = 900 Hex-Tiles brauchen wir keine Game-Engine. Der bestehende Canvas-Code lässt sich direkt auf Hex umstellen — statt fillRect malen wir beginPath + moveTo/lineTo für Sechsecke. Die Hex-Math kommt aus dem Red Blob Games Guide (Amit Patel), dem Standard-Referenzwerk das auch Civilization nutzt. Kein neues Package, ~200 Zeilen Code.
